いま広まるRAGとは
============================================================

- Retrieval-Augmented Generation
- ベクトルDB＋プロンプト拡張でLLMの幻覚削減
- 企業内ドキュメント検索、FAQ自動応答、レポート生成などで普及
- **強み:** 実装しやすい・既存テキスト資産を活用できる

.. note::
   グラフの話に入る前に、RAGの仕組みを簡潔にリマインド。図解があるとわかりやすい。

従来RAGの課題
============================================================

- ⚠️ 文書の粒度に依存しがちで、関係性の飛び越えが苦手
- 多段の意味推論やパス探索をLLMだけに任せるとコスト・時間が増加
- 構造化データやイベント系列を扱う際、情報の欠落が生じる
- キーワードベースのフィルタリングとの組み合わせが複雑化

.. note::
   具体例: 作者とスタッフのつながり、連載誌を跨ぐ文脈など。RAGだけでは拾いにくいケースを示す。

GraphRAGが拓く可能性
============================================================

- GraphDBで知識の構造をノード＋エッジとして表現
- 意味的な距離・パスを活用した探索が可能
- LLMへ渡すコンテキストを関係性込みで組み立てられる
- ハイブリッド検索（ベクトル＋グラフクエリ）で再現率と精度を両立

.. note::
   「構造化された知識をLLMに橋渡しする技術」と定義づけると腹落ちしやすい。

データセット: MADBとは
============================================================

- 📚 文化庁が公開するメディア芸術データベース（MADB）
- 漫画・アニメ・ゲームなどの作品情報を収録
- 作品、作者、スタッフ、雑誌、出版社、刊行年など多様な属性
- CC BY 4.0準拠で利用可能（要クレジット表記）

.. note::
   漫画領域にフォーカスする理由：人物・作品・メディアの関係がリッチでGraphRAGに向いている。

グラフモデリングの流れ
============================================================

1. データ収集: MADB APIからJSONをバッチ取得
2. 正規化: 作品／人／メディアなどのエンティティに分割
3. 関係抽出: 連載誌、原作者、作画担当、受賞歴をエッジ化
4. 付加情報: タグ、ジャンル、年代をノード属性へ格納
5. グラフDBへ投入: Neo4j / ArangoDB / Neptuneなどを選択

.. note::
   各ステップでスキーマ設計、正規化の工夫を紹介。具体的なツール（pandas, networkxなど）に触れる。

スキーマ設計の例
============================================================

.. list-table:: 主なノードとエッジ
   :header-rows: 1
   :widths: 30 40 30

   * - ノード
     - 主な属性
     - 主なエッジ
   * - Work (作品)
     - タイトル, 巻数, 連載開始年
     - ``(WORK)-[SERIALIZED_IN]->(MAGAZINE)``
   * - Person (作者/スタッフ)
     - 役割, 受賞歴, 外部ID
     - ``(PERSON)-[CREATED]->(WORK)``
   * - Magazine (雑誌)
     - 出版社, ターゲット層, 発行頻度
     - ``(MAGAZINE)-[PUBLISHED_BY]->(PUBLISHER)``
   * - Tag (ジャンル/テーマ)
     - タグ名, 信頼スコア
     - ``(WORK)-[HAS_TAG]->(TAG)``

.. note::
   グラフ図を表示できるとベター。テキストでも、エッジの向きと役割を強調する。

変換パイプライン（実装例）
============================================================

.. code-block:: text
   :caption: データ整形からグラフ投入まで（フローチャート）

   MADB API -> ETL Script -> Validation -> Graph DB Loader -> Neo4j
                                   |                         └-> Parquet Snapshot
                                   └-> Error Store

- Python: ``pydantic`` でスキーマ検証、``networkx`` でパス分析
- ローダー: ``neo4j-admin import`` や ``py2neo`` を用途で使い分け
- バッチ更新＋差分反映の設計で運用を簡潔に

.. note::
   Flow図を示すことで、ETLからグラフ投入までの全体像を共有。

API設計とユースケース
============================================================

- GraphQL or REST APIで作品・人物・タグを横断検索
- エントリポイント例
  - ``GET /works/{work_id}``
  - ``GET /works/{work_id}/related?max_depth=2``
  - ``POST /recommendations`` with query graph
- ユーザー向けUI: 作品検索、人物関係の探索、レコメンドの根拠表示
- 内部ユースケース: 編集部の企画検討、過去連載の再発掘、コラボ案の探索

.. note::
   レコメンド根拠の説明性（Explainability）を重視する点を強調。

グラフ可視化のアプローチ
============================================================

- 一覧: ``cytoscape.js`` / ``Sigma.js`` でWeb向け可視化
- 分析: ``Gephi`` や ``Neo4j Bloom`` でエキスパート向け探索
- LLM向け: パス抽出結果をナレッジパネル形式で整形
- 表現例
  - 共著者ネットワーク
  - 時系列アニメーション（連載年×作品数）
  - タグクラスタを組み合わせたリコメンド理由表示

.. note::
   スクリーンショットや動画があればデモであわせて紹介。

GraphRAGパイプライン
============================================================

1. ユーザーの自然言語クエリを受け取る
2. グラフ検索（パス探索＋属性フィルタ）で候補スニペットを抽出
3. コンテキストをテンプレートで整形（JSON / Markdown）
4. LLMへプロンプト投入し文章生成
5. 生成結果をスコアリングし、説明とともに返却

.. note::
   Pipelineの各ステップでの工夫（キャッシュ、非同期処理、レート制御）に触れる。

プロンプト設計の実例
============================================================

.. code-block:: text
   :caption: コンテキストプロンプトの骨子

   あなたは漫画編集部のリコメンドAIです。
   ユーザーの問い: {user_query}
   参考知識:
   {graph_context}

   制約:
   - 作品は最大3件
   - 各作品について推奨理由を2文以内で記述
   - 関係性（作者, 雑誌, タグなど）を引用

- Graph contextは ``path`` 単位でまとめるとLLMが読みやすい
- 温度と最大トークンを低めに設定し、説明を安定化
- 評価: ``LLM-as-a-judge`` + 人手で品質を監視

.. note::
   プロンプトに制約とフォーマットを明示することの重要性を強調。
